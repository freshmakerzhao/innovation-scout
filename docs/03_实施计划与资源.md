# 4–8 周实施计划与资源

状态：2026-09-24 修订稿。默认 **2 名全职开发人员 + 兼职领域专家/科技服务人员**；从一个产业方向、三个主题、模型账户和专利数据路径明确后的启动日计算。第 4 周交可演示版，第 6 周交内部试用版，第 7–8 周按试用反馈修正。

## 每周成果

| 周次 | 复用与新增工作 | 当周可检查结果 |
| --- | --- | --- |
| W1 | 锁定上游版本，跑通 GPT Researcher 的模型、OpenAlex 检索、现有页面和报告；确认 3 个主题及样本 | 一次真实研究演示、启动说明、模型/来源花费样本、许可证核查记录 |
| W2 | 在 `app/pilot_ext/` 做 OpenAlex 按日期监测、SQLite 主题/来源表、去重和每日任务 | 主题可保存、手动/定时运行，候选有 DOI/来源/时间，失败可重试 |
| W3 | 接入 EPO OPS 的小范围专利查询并转换为候选；同时支持授权样本导入 | 至少 20 条真实专利样本可回查，配额和错误可见 |
| W4 | 调用现有研究代理生成带出处的简报；新增机会卡草稿、人工编辑/批准与 Markdown/HTML 导出 | 完成[会议稿](00_会议讨论稿.md)所列现场演示；抽查 5 张机会卡 |
| W5 | 录入 3–5 条企业需求卡，对照候选机会并记录适配/不适配理由 | 业务人员对 5–10 个候选作人工判断，留反馈 |
| W6 | 修复试用问题、限制内部访问、整理安装/备份/恢复和接口额度；做 7 天运行与来源抽查 | 1–3 人内部试用，通过[验收表](01_产品范围与验收.md)并出误差清单 |
| W7–W8 | 仅处理验收阻塞、来源质量与体验问题；决定下一阶段 | 修订版和下一阶段任务，不自动扩成全平台 |

**前置条件**：W1 必须有可用模型 API、OpenAlex key、一个业务方向和审核人；EPO OPS 账号尽量在 W2 前获得。若专利账号迟到，W3 可用授权数据导入完成界面和数据合同，但第 6 周对外部专利接口的验收顺延，并在报告中标记。

## 人员和分工

| 角色 | 6 周投入 | 主要负责 |
| --- | --- | --- |
| 开发 A（Python/数据） | 全职 | 上游启动、OpenAlex/EPO 适配、主题任务、SQLite 与运行日志 |
| 开发 B（页面/集成） | 全职 | 现有 UI 定制、报告/机会卡、需求对照、安装和导出 |
| 领域专家 | 每周约半天 | 主题词、20+20 条样本、方法与复用条件核验 |
| 科技服务人员/验收人 | 每周约半天 | 企业需求、机会卡审核、试用和联系决策 |

约 **3–4 人月**用于第 6 周试用版；第 7–8 周若全员继续投入，追加约 1–2 人月。只有 1 名开发者时，上述完整范围预计超过 8 周，应优先交付论文监测和人工机会卡，再接专利与需求对照。

## 软件与账户

- 复用上游的 Python 3.11+、FastAPI、研究代理、现有轻量页面及 Docker Compose。开发可直接用 Python 环境；若使用其 NextJS 页面，再准备 Node 与包管理器。确切版本按上游锁文件和安全更新确定。
- 本地/服务器需要 Docker、Git、SQLite（Python 内置支持）、定时任务服务和 HTTPS/内网访问入口。
- 外部账户：模型服务密钥、OpenAlex 免费 key、EPO OPS 注册/OAuth 凭据；是否使用通用网页检索服务由演示范围决定。只通过许可的接口获取数据。
- **不新增** Django、PostgreSQL、Redis、Celery、独立向量库或 GROBID 到首版关键路径；试用证明需要时再选。

## 硬件

| 环境 | 建议配置 | 说明 |
| --- | --- | --- |
| 开发机 | 6–8 核 CPU、16 GB RAM、至少 50 GB 可用 SSD | 运行原项目、样本任务和开发页面；Docker/NextJS 同时启动时 32 GB 更宽裕 |
| 共享试用服务器 | 4–8 vCPU、16 GB RAM、100–200 GB SSD | 1–3 位内部用户、三个主题、每日约百条候选；先测真实查询和报告耗时 |
| 备份 | 独立位置 ≥100 GB | SQLite、配置和获准保存的导出物；至少一次恢复演练 |
| GPU | 首版无需 | 使用已获批准的模型 API；私有模型选型另做容量测试与预算 |

服务器通过内网或 VPN 开放，不直接公网部署现有页面。若机构要求私有部署和本地模型，第 1 周需重新估算硬件及工期。

## 费用口径

1. **人力**：第 6 周约 3–4 人月 × 实际岗位成本，是主要费用。
2. **基础设施**：一台试用服务器、备份空间、网络和监控按实际报价 × 2 个月；可复用已有服务器。
3. **模型**：以每天最多 10 份深度报告为控制上限，若每份平均 20,000 输入 token、2,000 输出 token，30 天约 600 万输入和 60 万输出 token。费用 = 实测用量 × 选定服务当期单价；查询、重试、嵌入另计。
4. **数据接口**：[OpenAlex](https://help.openalex.org/access/pricing/)免费 key 当前有每日用量预算，超额另计；[EPO OPS](https://www.epo.org/en/searching-for-patents/data/web-services/ops)当前免费阈值为每周 4 GB，超额有订阅。首版控制样本规模，不购买全量数据库。

以上是容量估算，不是云厂商报价。W1 以真实一次研究的耗时、token 和 API 响应更新预算；任何数据采购或对外部署另列决定。

## 主要风险

| 风险 | 对 6 周的影响 | 处理 |
| --- | --- | --- |
| 上游环境和模型配置与本机不符 | W1 基线不能启动 | 先用已有页面和单来源最小配置，记录版本；W1 未通过则调整范围 |
| EPO 凭据/额度/条款未落实 | 专利自动检索延迟 | 用授权样本保留演示，明确接口验收未完成 |
| 报告引用不实或结论过度 | 机会卡不能外发 | 强制原始链接、人工审核和“未知项” |
| 扩展直接改动上游核心太多 | 后续合并困难 | 新功能集中于 `pilot_ext/`，核心改动逐条记录并测试 |
| 用户要求多人正式生产服务 | SQLite/现有页面的权限不足 | 作为 V0.2 单独立项，迁移数据库、认证和审计 |
